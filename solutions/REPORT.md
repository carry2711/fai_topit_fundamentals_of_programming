## 1. Задание 1. Условия и классификация данных

### 1.1. Алгоритм обработки

```text
ФУНКЦИЯ process_record(score, work_type, absences):
    ЕСЛИ НЕ (0 <= score <= 100):        ВЕРНУТЬ строку ошибки о балле
    ЕСЛИ НЕ (0 <= absences <= 5):       ВЕРНУТЬ строку ошибки о пропусках
    level ← classify_score(score)        # 90/75/60 — границы уровней
    ЕСЛИ absences > 3:  level ← downgrade(level)
    work ← describe_work(work_type)      # match/case
    ВЕРНУТЬ готовую строку
```

### 1.2. Порядок проверки условий 

1. **Сначала валидация диапазонов** (`if not (0 <= score <= 100)` → ранний `return`).
   Пока данные не проверены, классифицировать их нельзя: балл 150 попал бы в ветвь «отличный».
2. **Затем уровень по баллу** — цепочка `if / if / if` с ранними `return` от старшей границы к младшей:
   `>= 90` → `>= 75` → `>= 60` → иначе «недостаточный».
   Благодаря порядку сверху вниз не нужно писать двойные условия вида `75 <= score <= 89`.
3. **Потом понижение за пропуски** — отдельная функция `downgrade()`, работающая со списком-шкалой
   `["отличный", "хороший", "удовлетворительный", "недостаточный"]`.
   Понижение = шаг вправо по шкале с защитой `idx + 1 < len(order)`.
4. **В конце `match / case`** по типу работы — это независимая от баллов ветвь, поэтому она последняя.

### 1.3. Недостижимые ветви при выбранном порядке

| Ветвь / условие | Достижима? | Причина |
|---|---|---|
| `score >= 75` при `score >= 90` | нет | старшая ветвь уже сделала `return` |
| `score < 0` внутри `classify_score()` | нет | такие значения отсекает валидация в `process_record()` |
| `return level` в конце `downgrade()` (без понижения) | нет при текущих вызовах | вызывается только для уровней выше «недостаточного»; ветвь оставлена как защита контракта |
| `case _` в `describe_work()` | достижима только при неизвестном типе | по условию тип один из трёх, но ветвь обязательна для устойчивости (проверена сценарием № 10) |

## 2. Задание 2. Циклы и базовые алгоритмические схемы

Исходные данные: `measurements = [12, 15, 11, 18, 18, 9, 21, 15, 7, 18]`

### 2.1. Разделение на этапы

* **Этап 1 (один проход).** Сумма, минимум, максимум, количество чётных — всё считается в одном цикле.
  Минимум и максимум инициализируются **первым элементом**, а не нулём: иначе для списка из отрицательных чисел максимум остался бы нулём.
* **Этап 2 (второй проход).** Среднее = сумма / n становится известно только после первого прохода, поэтому подсчёт «больше среднего» физически невозможен в том же цикле.
* **Этап 3.** Линейный поиск числа, введённого пользователем (`-1`, если числа нет).
* **Этап 4.** Проверка простоты, сортировка выбором, бинарный поиск и сравнение числа сравнений.

### 2.2. Псевдокод 

**Алгоритм 1. Статистика за один проход**

```text
ВХОД: непустой список a длины n
total ← 0; mn ← a[0]; mx ← a[0]; even ← 0
ДЛЯ КАЖДОГО x ИЗ a:
    total ← total + x
    ЕСЛИ x < mn: mn ← x
    ЕСЛИ x > mx: mx ← x
    ЕСЛИ x mod 2 = 0: even ← even + 1
ВЕРНУТЬ (total, mn, mx, even)

ВТОРОЙ ПРОХОД:
avg ← total / n; cnt ← 0
ДЛЯ КАЖДОГО x ИЗ a:
    ЕСЛИ x > avg: cnt ← cnt + 1
```

**Алгоритм 2. Сортировка выбором**

```text
ВХОД: список a длины n;  a ← копия входа (исходник не меняем)
cmp ← 0
ДЛЯ i ОТ 0 ДО n-1:
    min_idx ← i
    ДНЯ j ОТ i+1 ДО n-1:
        cmp ← cmp + 1
        ЕСЛИ a[j] < a[min_idx]: min_idx ← j
    ОБМЕНЯТЬ a[i] и a[min_idx]
ВЕРНУТЬ (a, cmp)
```

**Алгоритм 3. Бинарный поиск**

```text
ВХОД: отсортированный по возрастанию список a, значение target
lo ← 0; hi ← n - 1; cmp ← 0
ПОКА lo <= hi:
    cmp ← cmp + 1
    mid ← (lo + hi) // 2
    ЕСЛИ a[mid] = target: ВЕРНУТЬ (mid, cmp)
    ЕСЛИ a[mid] < target: lo ← mid + 1
    ИНАЧЕ:                hi ← mid - 1
ВЕРНУТЬ (-1, cmp)
```

**Алгоритм 4. Проверка простоты**

```text
ЕСЛИ n < 2:      ВЕРНУТЬ Ложь
ЕСЛИ n = 2:      ВЕРНУТЬ Истина
ЕСЛИ n mod 2=0:  ВЕРНУТЬ Ложь
d ← 3
ПОКА d * d <= n:
    ЕСЛИ n mod d = 0: ВЕРНУТЬ Ложь
    d ← d + 2
ВЕРНУТЬ Истина
```

Условие `d * d <= n` эквивалентно `d <= √n`, но не требует `math.sqrt` и не имеет погрешности округления.

### 2.4. Сравнение линейного и бинарного поиска (основной результат — число сравнений)

Оба алгоритма запускались на **одинаковых** наборах `list(range(n))`, искомое значение — последний элемент (худший случай для линейного поиска).

| n | Сравнений: линейный | Сравнений: бинарный | Сравнений при сортировке выбором | Выигрыш бинарного |
|---:|---:|---:|---:|---:|
| 10 | 10 | 4 | 45 | ×2.5 |
| 100 | 100 | 7 | 4 950 | ×14.3 |
| 1000 | 1000 | 10 | 499 500 | ×100 |

Фактический вывод программы:

```text
=== Сравнение линейного и бинарного поиска ===
     N |   линейный |   бинарный
    10 |         10 |          4
   100 |        100 |          7
  1000 |       1000 |         10
```

**Правило подсчёта сравнений.** В линейном поиске считается каждое сравнение `x == target`. В бинарном поиске считается одна «проба» — обращение к середине на каждой итерации цикла (внутри неё до двух поэлементных сравнений: `==` и `<`). Даже если считать по 2 сравнения на итерацию, получим 8 / 14 / 20 против 10 / 100 / 1000 — вывод не меняется.

**Важный вывод.** Бинарный поиск выигрывает только на **отсортированных** данных. Сортировка выбором стоит ~n²/2 сравнений, поэтому для однократного поиска дешевле линейный поиск. Бинарный поиск оправдан, когда данных много и поисков много, а сортировка выполняется один раз.

### 2.5. Почему ограничение делителей квадратным корнем корректно

Пусть составное `n = a · b`, где `1 < a ≤ b < n`. Если бы **оба** делителя были больше `√n`, то
`a · b > √n · √n = n` — противоречие с `a · b = n`.
Значит, у любого составного числа существует делитель `a ≤ √n`. Следовательно, если ни один делитель из диапазона `[2, √n]` не найден, число простое. Перебирать большие делители бессмысленно: для каждого `b > √n` парный ему `a < √n` уже проверен.

### 2.6. Оценки сложности

| Алгоритм | Время | Доп. память | От чего зависит число операций |
|---|---|---|---|
| Сумма / min / max / чётные (1 проход) | O(n) | O(1) | n — длина списка; 4 элементарные проверки на элемент |
| Подсчёт «больше среднего» (2 проход) | O(n) | O(1) | n; всего два прохода = 2n ≈ O(n) |
| Линейный поиск | лучший O(1), худший/средний O(n) | O(1) | позиция искомого: 1 … n сравнений |
| Бинарный поиск | O(log₂ n) | O(1) | каждый шаг уменьшает область вдвое: n → n/2 → … → 1 |
| Сортировка выбором | O(n²) всегда | O(n) из-за копии (сам алгоритм in-place, O(1)) | число сравнений ровно n(n−1)/2, не зависит от порядка данных |
| Проверка простоты | O(√n) | O(1) | число нечётных делителей до √n ≈ √n / 2 |

Память O(1) означает: несколько скалярных переменных (`total`, `mn`, `mx`, `lo`, `hi`, `d`), не зависящих от n.

### 3.2. Студенты, сдавшие обе работы (операции над множествами)

```python
s1 = {st for st, lab in best if lab == "lab_01"}   # {'anna','boris','daria'}
s2 = {st for st, lab in best if lab == "lab_02"}   # {'anna','boris'}
result = s1 & s2                                   # пересечение
```

* До добавления записи: `{'anna', 'boris'}`
* После добавления `("daria", "lab_02", 4)`: `{'anna', 'boris', 'daria'}`

### 3.3. Инкрементальное обновление (без полного перестроения)

Функция `add_record()` выполняет ровно 5 действий константной стоимости:

```text
students.add(student)                       # O(1)
labs.add(lab)                               # O(1)
attempts[student].append((lab, score))      # O(1) амортизированно
best[(student, lab)] ← max по правилу       # O(1)
attempts_count[(student, lab)] += 1         # O(1)
```

Проверка: добавили `("daria", "lab_02", 4)` →
`best[('daria','lab_02')] = 4`, `attempts_count[('daria','lab_02')] = 1`, множество сдавших обе работы расширилось. Пересборка всех структур не потребовалась.

### 3.4. Обоснование выбора коллекций

* **Множество подходит для уникальных значений.** `set` хранит только хэши элементов, автоматически отбрасывает дубликаты (`students.add("anna")` дважды не изменит множество) и даёт проверку принадлежности за O(1). additionally доступны `&`, `|`, `-`, что и позволило одной строкой найти сдавших обе работы.
* **Кортеж можно использовать как ключ словаря.** Кортеж неизменяем, поэтому его хэш стабилен на всём протяжении жизни: `hash(("anna", "lab_01"))` не изменится. Это позволяет адресовать результат по **составному ключу** без вложенных словарей.
* **Список нельзя использовать как ключ.** Список изменяем, `list.__hash__` равен `None`, и попытка `d[[1,2]]` вызывает `TypeError: unhashable type: 'list'`. Если бы список был ключом, изменение его содержимого изменило бы хэш, и элемент «потерялся» бы в хэш-таблице — целостность словаря нарушилась бы.
* **Словарь предпочтительнее списка для частого поиска по составному ключу.** В словаре поиск `best[(student, lab)]` — O(1) в среднем. В списке кортежей пришлось бы каждый раз просматривать все записи — O(n). При m запросах разница составляет O(m) против O(m·n).

### 3.5. Средняя сложность операций

| Коллекция | Добавление (среднее) | Поиск (среднее) | Худший случай | Память |
|---|---|---|---|---|
| `set` | O(1) | O(1) | O(n) при массовых коллизиях хэшей | O(k) |
| `dict` (ключ-кортеж) | O(1) | O(1) | O(n) | O(k) |
| `list.append` | O(1) амортизированно | — | O(n) при расширении буфера | O(k) |
| `list` — поиск по значению | — | O(n) | O(n) | O(k) |
| Построение всех структур | O(n) | | | O(n) |
| Запрос `completed <lab>` | O(k), k — число пар в `best` | | | O(k) |

Хэширование строки/кортежа стоит O(длины ключа), но длина ключа ограничена и не растёт с числом записей, поэтому считается константой.

## 4. Задание 4. Функции, параметры и области видимости

### 4.1. Контракты реализованных функций

Все функции **не изменяют** переданные коллекции: `arithmetic_mean` только читает, `normalize_name` создаёт новые строки, `collect_tags` накапливает результат в собственном списке, `apply_to_results` возвращает новый список.

### 4.4. Исследование LEGB

Фрагмент кода:

```python
course = "Python"                  # G: глобальная область (модуль)

def outer():
    course = "Advanced Python"     # E: объемлющая (enclosing)
    def inner():
        nonlocal course            # привязка к E, а не к L и не к G
        course = "Inner: " + course
    inner()
    return course
```

**Схема областей видимости:**

```text
┌──────────────────────────────────────────────────────────────┐
│ B — Built-in:  print, len, range, str, TypeError, ...        │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ G — Global (модуль task_4.py):                         │  │
│  │     course = "Python"                                  │  │
│  │     outer, arithmetic_mean, build_report, ...           │  │
│  │  ┌──────────────────────────────────────────────────┐  │  │
│  │  │ E — Enclosing (outer):                           │  │  │
│  │  │     course = "Advanced Python"  ← ячейка closure  │  │  │
│  │  │  ┌────────────────────────────────────────────┐  │  │  │
│  │  │  │ L — Local (inner):                         │  │  │  │
│  │  │  │     nonlocal course → пишет в E             │  │  │  │
│  │  │  │     своих имён не создаёт                   │  │  │  │
│  │  │  └────────────────────────────────────────────┘  │  │  │
│  │  └──────────────────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘

Порядок поиска имени: L → E → G → B
Порядок записи без nonlocal/global: всегда L (создаётся новое локальное имя)
```

**Разбор поиска каждого использованного имени:**

| Имя | Где найдено | Путь поиска | Комментарий |
|---|---|---|---|
| `course` в `inner()` | **E** | L(нет, из-за `nonlocal`) → **E** | читается и записывается ячейка объемлющей функции |
| `course` в `outer()` | **E** (локальная для `outer`) | L → найдено | это отдельное имя, скрывает глобальное |
| `course` на уровне модуля | **G** | L=G → найдено | остаётся `"Python"` |
| `print` | **B** | L → E → G → **B** | встроенное имя |
| `arithmetic_mean` внутри `build_report` | **G** | L → **G** | функция определена на уровне модуля |
| `values`, `total` в `arithmetic_mean` | **L** | **L** | параметры и локальные переменные |
| `threshold` в `checker` | **E** | L → **E** | значение из вызова фабрики (замыкание) |
| `results` в `add_result_fixed` | **L** | **L** | параметр |

Фактический вывод демонстрации:

```text
LEGB demo:
  global course = Python
  after outer() = Inner: Advanced Python
  global course после = Python
```
`nonlocal` поднимается ровно на один уровень (в E), а не до G. Для изменения глобального имени потребовался бы `global`.

### 4.5. Ошибка изменяемого значения по умолчанию

Исходная («сломанная») функция:

```python
def add_result_broken(value, results=[]):
    results.append(value)
    return results
```

**Жизненный цикл объекта значения по умолчанию:**

1. Значения по умолчанию вычисляются **один раз — в момент выполнения `def`**, а не при каждом вызове.
2. Созданный список сохраняется в атрибуте `add_result_broken.__defaults__` и живёт столько же, сколько сама функция (то есть весь сеанс работы модуля).
3. Каждый вызов без второго аргумента получает **ссылку на тот же самый список**.
4. `append` мутирует этот общий объект → результаты «протекают» из вызова в вызов.

Фактическая демонстрация:

```text
--- mutable default ---
[1]          # add_result_broken(1)
[1, 2]       # add_result_broken(2)  ← ОШИБКА: ожидалось [2]
[1]          # add_result_fixed(1)
[2]          # add_result_fixed(2)   ← правильно
```

**Исправление — «сентинел» `None`:**

```python
def add_result_fixed(value, results=None):
    if results is None:
        results = []      # новый список на каждый вызов
    results.append(value)
    return results
```

Теперь по умолчанию хранится неизменяемый `None`, а список создаётся заново при каждом вызове. Правило: **в качестве значения по умолчанию допустимы только неизменяемые объекты** (`None`, числа, строки, кортежи).

### 4.6. Практическое расширение: функции как значения и замыкания

```python
apply_to_results(lambda x: x * 2, [1, 2, 3])          # [2, 4, 6]
apply_to_results(arithmetic_mean, [[1, 2], [10, 20]]) # [1.5, 15.0]
```

`apply_to_results(operation, values)` — функция высшего порядка: параметр `operation` сам является функцией, поэтому реализация не зависит от конкретной операции (принцип «открытости»).

**Фабрика проверок:**

```python
def make_threshold_checker(threshold):
    def checker(value):
        return value >= threshold
    return checker

check_50 = make_threshold_checker(50)
check_80 = make_threshold_checker(80)
check_50(60)   # True
check_80(60)   # False
```

Фактический вывод:

```text
--- apply_to_results ---
[2, 4, 6]
[1.5, 15.0]
check_50(60) = True
check_80(60) = False
```

**Что сохраняется в замыкании.** Каждый вызов фабрики создаёт **свою** ячейку (cell) для переменной `threshold`. Возвращаемая `checker` держит ссылку на эту ячейку, поэтому `threshold` живёт даже после завершения `make_threshold_checker`. Две проверки полностью независимы: у `check_50` в замыкании 50, у `check_80` — 80 (это видно через `check_50.__closure__[0].cell_contents`). Сохраняется **сама переменная-ячейка, а не копия значения**, поэтому при изменении `threshold` через `nonlocal` изменение увидели бы все ссылки на эту ячейку.

## 5. Задание 5. Анализатор учебных результатов

### 5.1. Принятое правило для пустого списка результатов

Единое правило, зафиксированное во всех функциях:

> Студент без результатов **не участвует** в числовой статистике: `mean = 0.0`, `min = None`, `max = None`, категория — `"нет данных"`. Такой студент не может стать лидером и не попадает ни в одну из четырёх числовых категорий, но учитывается в общем количестве студентов.

Это позволяет не падать на пустых данных и не искажать средний балл группы фиктивным нулём.

### 5.2. Контракты публичных функций

### 5.5. Неизменность исходных данных

* `group_summary` строит **новые** списки `summaries` и `all_values`, входной словарь только читается.
* `find_top_students` создаёт новый словарь средних `avgs` и возвращает новый список имён — исходный словарь не мутируется.
* Рейтинг формируется без `sorted()` над исходным словарём и без изменения порядка его ключей: сначала находится максимальное среднее (`maximum`), затем одним проходом собираются все студенты с этим значением.
* Контроль: после всех вызовов `students` побайтово совпадает с исходным (проверено сравнением с копией).

### 5.6. Оценка сложности построения статистики

Обозначения: **S** — число студентов, **N** — общее число всех оценок (N = Σ длин списков).

| Функция | Время | Доп. память | Обоснование |
|---|---|---|---|
| `mean` / `minimum` / `maximum` | O(k) | O(1) | один проход по k элементам |
| `classify` | O(1) | O(1) | ≤ 3 сравнений |
| `student_summary` | O(k) | O(1) | три прохода по списку = 3k ≈ O(k) |
| `group_summary` | **O(S + N)** | O(S + N) | по каждому студенту O(k), в сумме O(N); сборка `all_values` — O(N); подсчёт категорий — O(S) |
| `find_top_students` | O(S + N) | O(S) | средние — O(N), максимум по S средним — O(S), сбор лидеров — O(S) |
| `format_report` | O(S) | O(S) | одна строка на студента |
| **Итого** | **O(S + N)** — линейно от объёма данных | O(S + N) | константное число проходов |

Так как обычно N ≫ S, итоговая оценка — **O(N)**, то есть время растёт линейно с числом оценок.

## 8. Выводы

1. **Порядок условий важнее их количества.** Ранний `return` при валидации убирает вложенность и делает часть последующих проверок заведомо недостижимыми — это упрощает чтение кода, но такие «мёртвые» ветви нужно осознавать и оставлять только как защиту контракта.
2. **Число проходов диктуется зависимостями данных.** Сумму, минимум, максимум и количество чётных можно получить за один проход, а «больше среднего» — только за второй, потому что среднее зависит от полной суммы.
3. **Структура данных определяет сложность.** Замена списка кортежей на словарь с кортежным ключом превратила поиск результата из O(n) в O(1), а множества позволили выразить «сдал обе работы» одной операцией `&`.
4. **Число сравнений — более честная метрика, чем время.** На 1000 элементов линейный поиск сделал 1000 сравнений, бинарный — 10. Но с учётом стоимости сортировки (499 500 сравнений) бинарный поиск выгоден только при многократных запросах к уже отсортированным данным.
5. **Значения по умолчанию живут вместе с функцией.** Изменяемый default — источник скрытых ошибок; правильный приём — `None` + создание объекта внутри тела функции.
6. **LEGB объясняет поведение имён без «магии».** `nonlocal` поднимает запись ровно на один уровень вложенности, `global` — до модуля; замыкание сохраняет ячейку переменной, а не её мгновенную копию.
7. **Как декомпозиция повлияла на читаемость.**
   * Каждая функция решает одну задачу и умещается на экран — код читается сверху вниз без прокрутки.
   * Аннотации типов и docstring работают как контракт: сразу видно, что можно передать и что вернётся, включая особые случаи.
   * Вычисления отделены от вывода: `group_summary` ничего не печатает, `format_report` ничего не считает — любую часть можно переиспользовать и протестировать отдельно.
   * Особые случаи (пустой список, пустая группа, несколько лидеров) сосредоточены в одном месте, а не размазаны по программе — исчезли дублирующиеся проверки.
   * `main()` превратился в короткий сценарий, который читается как оглавление задачи; отладка сводилась к проверке одной маленькой функции, а не всего скрипта.
   * Итог: программа из «простыни» превратилась в набор независимых кирпичиков, каждый из которых можно понять, проверить и заменить, не ломая остальные.
